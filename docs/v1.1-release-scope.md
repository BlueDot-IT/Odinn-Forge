# Ódinn Forge 1.1 release scope

_Status: active release-candidate scope and feature freeze._

Ódinn Forge 1.1 consolidates the systems already present on the `1.1.0-rc.3`
release-candidate line. The bounded agent-graph and host-capability foundation
slices on that line remain opt-in and experimental; they do not promote a new
runtime surface to stable or enlarge the v1 compatibility promise. Work
admitted during this freeze must improve an existing boundary, repair a defect,
reduce host complexity, strengthen verification, or make an existing operator
outcome clearer.

The [v1 compatibility policy](v1-compatibility.md) and
[surface matrix](surface-matrix.md) remain authoritative. This document decides
which already-implemented systems are release deliverables; it does not promote
an experimental interface to stable by implication.

## Stable 1.1 deliverables

- The supported local, single-user product and its existing v1 compatibility
  promise.
- Versioned, explicitly validated application outputs for status, diagnostics,
  and session listing, with the existing CLI and gateway response behavior
  preserved.
- One shared operator read plane for runtime health, durable work, approvals,
  recovery, and audit summaries across CLI, TUI, HTTP JSON, and the local
  console.
- Existing task, durable-job, approval, audit, restart-recovery, update,
  rollback, backup, restore, and uninstall guarantees.
- Incremental CLI and gateway decomposition that establishes command and route
  modules without changing kernel authority or transport security.
- Complete repository dependency-direction enforcement for source imports and
  workspace package manifests.
- A separately built local-console frontend whose authentication, loopback
  bootstrap, origin checks, response contracts, manifest, and restrictive CSP
  remain unchanged. The source extraction is complete; protected cross-platform
  downloaded-candidate verification remains a release gate.

## Present but not promoted

The following remain available under the classifications already recorded in
the surface matrix:

- Run verification, policy preview, restore points, governed workspace actions,
  and model routing remain core advanced services with experimental advanced
  interfaces.
- Capability tokens, portable run bundles, and scenario comparison remain
  disabled-by-default optional experimental modules.
- Durable workflows, event ingress, project context, Agent SDK packages, Skill
  SDK packages, MCP packages, messaging channels, multi-user hosting, and
  multi-agent graphs remain experimental surfaces.
- Multi-tenancy remains an experimental first tranche; it does not grant
  hostile-tenant isolation and has no stable compatibility promise.

## Release criteria

Do not publish `v1.1.0` stable until all of the following are true:

1. Application read outputs reject malformed, oversized, secret-bearing, or
   incompatible port values before presentation.
2. The operator snapshot is produced through one application use case rather
   than independently assembled by each presentation host.
3. Issue #118's approval-continuation behavior is fixed with strict run, tool,
   resource, actor, exact-input, expiry, denial, cancellation, and replay
   regression coverage.
4. Initial CLI and gateway module extraction has landed and new behavior is no
   longer added directly to their legacy command or route blocks.
5. Source imports and package manifests pass the complete architecture matrix.
6. The dependency update stream keeps TypeScript 7 and Node 26 type definitions
   out of routine release-candidate updates.
7. Every command in [release validation](release-validation.md) passes against
   the exact tagged artifact, including installation, onboarding, provider,
   restart, recovery, rollback, audit, checksum, SBOM, provenance, and
   downloaded-asset verification. Validating exact downloaded release artifacts
   on GitHub-hosted Linux, macOS, and Windows runners is a publication
   dependency; maintainer-owned physical clean machines are not required.
8. No unresolved security or release-blocking defect is being hidden by a
   synthetic check or an experimental classification.

Removing every large source file, completing the full kernel decomposition,
migrating to TypeScript 7, or promoting an experimental surface is not a 1.1
release blocker. Those changes require their own evidence and must not delay or
destabilize this candidate.

## Change admission during the freeze

A change may enter the 1.1 candidate only when it:

- has a bounded outcome and an explicit compatibility statement;
- preserves centralized policy, approval, audit, recovery, and uncertainty
  enforcement;
- includes focused regression coverage and packaged-artifact coverage when the
  build or distribution changes;
- does not broaden a default capability, feature flag, network path, or trust
  boundary; and
- can be reviewed and reverted independently.

Everything else waits for the post-1.1 development line.
